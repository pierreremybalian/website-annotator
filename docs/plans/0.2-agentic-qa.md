# 0.2: element picking, agentic QA, Astro

## Why
- Drawn boxes drift when the window resizes. A box is stored as fractions of a large container, which reflows. Picking a DOM element keeps the highlight on the element at every size.
- QA issues should be fixable by coding agents. Agents get structured JSON through a **CLI**: no MCP server and no standing context cost. They get enough context to find the source file, and they hand issues back for human confirmation.
- Sites aren't only WordPress. Astro builds are first-class: the core is platform-agnostic, and each platform gets a thin adapter.

## Decisions
- **Element picking is the default.** Hover highlights the element with an overlay (never by changing the page's styles). ↑/↓ or the wheel walk to the parent or child. Click selects. "Draw area" (toggle or Shift-drag) stays as a fallback and snaps to an element it covers ≥80%. `Anchor.mode = 'element' | 'area'`; a missing mode means area (pre-0.2 reports).
- **Pins in element mode** outline the element's live rect. If the element isn't visible at the current size, the pin is hidden and listed in a new **page issues panel** as "not visible at this screen size (reported at 1440px)".
- **Context capture works on any platform.** Always captured: element HTML (trimmed, form values stripped), tag, text, nearest heading/landmark, key computed styles. Source hints, nearest first:
  - `data-annotate-source`
  - `data-annotate-block` (WordPress block name)
  - `data-astro-source-file` / `-loc` (Astro dev)
  - `data-astro-cid-*` (Astro production)

  The page context comes from `window.AnnotateContext`, which each adapter sets.
- **Adapters**
  - **WordPress plugin:** sets `AnnotateContext` (post ID, post type, template, slug) and adds `data-annotate-block` to rendered blocks. Block names only, so no file paths end up in public HTML; the CLI resolves names to files in the repo.
  - **`@annotate/astro` (new):** an integration that injects the widget and provides source hints for components.
- **New `review` status.** Agents move issues to "Ready for review" (a Trello list). They can never close issues. On the pin, a client or teammate clicks **Confirm** (→ Done) or **Still broken** (→ New, with a note).
- **Agent API** (`/v1/agent/*`, `Authorization: Bearer at_…`; hashed per-project agent tokens, separate from the widget's public access key): project, issues (filter by status/url), issue detail by **number**, claim/release (lease), comment, resolve, reopen, and allowed origins.
- **CLI `annotate`** (`packages/cli`, single-file Node, no runtime deps). Every command takes `--json`.
  - `connect`: new project via the Trello popup.
  - `init`: link this repo to an existing project via the same popup.
  - `issues`, `show`, `screenshot`, `claim`, `release`, `comment`, `resolve`, `reopen`, `origins list|add|remove`, `skill`.
  - Config lives in `.annotate.json` (gitignored); the `ANNOTATE_TOKEN` env var overrides the token.
  - The browser hands keys to the CLI with a device-style flow: the CLI creates a session with a verifier hash, opens `/connect?cli=<id>`, and polls with the verifier.
- **Claude Code skill** (`annotate skill install` writes `.claude/skills/annotate-qa/SKILL.md` into the repo). The routine: list → claim → locate the source → fix → resolve.
